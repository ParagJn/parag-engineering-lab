## Test and harness lessons (they cost time to learn)
- Any test that builds an app uses `make_settings`; an autouse guard in `tests/conftest.py` fails any test that opens `backend/data`. Never delete real database rows.
- `tests/test_guardrails_repo.py` forbids secret-shaped strings written in full; build fake secrets from fragments (`tests/_fakes.py`).
- Mutation harness: `python -u -m scripts.mutation_check <mutants file> --tests <files>`. It has a baseline guard, treats a hung suite as INVALID, runs each mutated suite in its own session, and `--only` matches by substring (one text). To run a chosen few, write a small batch file that filters `MUTANTS` by name (see how `/tmp/s16_new.py` was built: import the full mutants module, filter `m.MUTANTS`).
- Run long mutation sweeps in batches of about six, each under ~280 seconds with `timeout`; a single command over ~10 minutes gets killed (exit 144). Killed sweeps can leave `time.sleep(120)`/`(60)` processes behind: check with `pgrep -f "sleep\((120|60)\)"` and ask before killing.
- Delete redundant code rather than test it; pin literals; one fault per test. A new survivor means write a real test, not a looser mutant.
- To look at an SVG, wrap it in HTML and render with the Swift/WebKit tool at `/tmp/shot/shot` (it may need rebuilding after a reboot; `/tmp` is cleared).

## Harness lesson (2026-11-03)
A mutation batch run under `timeout` kills the harness but can leave the mutated suite running (a deliberately broken loop never ends). One such orphan ran for hours and made `test_scratch_folders_are_removed_after_each_command` fail in the full suite, because that test compares the whole machine's temp folder. Before a full-suite run, check `ps -u $(id -u) -o pid=,etime=,command= | grep -E "pytest|mutation_check"`; the user stops an orphan with `! kill <pid>` (the assistant's kill is blocked). Prefer short batches (3 mutants, about 100 seconds) run in the background with a log. Old `sdlc_mutation_*` folders in the system temp directory are safe to delete.

## Lessons from 17c (2026-11-03)
- **A flaky test is a bug until proven otherwise.** The one-in-five Build phase failure passed 14 times alone and failed only in company. The cure was to make the test say WHY an artefact failed (`assert [(o.key, o.reason) ...] == []`), then loop the whole file until it failed and read the traceback. Never re-run until green.
- **A tool that is only there to tidy up can be the bug.** Removing the empty shared `.stage` folder raced with another writer making a folder in it. The tidy-up and its tool were deleted.
- **A put-back must name what it puts back.** Anything that restores 'the saved version' of a component must skip components that have no saved version yet and are being written right now.
- **A flake can be a real race that only the full suite shows (18b).** `replace_folder` asked 'does it exist' and then 'is it a folder' as two looks; under the full suite's timing another writer moved the folder in between and it read as a file. Never dismiss a one-in-N failure: make the test say why, then pin the cause with a deterministic test (monkeypatch the two looks).
- **A mutation sweep finds bugs, not only gaps (18b).** Two of the 17 survivors were real faults in the new code (a person's edit read as 'unverified'; a hand edit of the review hid both results). Read each survivor as a question about the code, not just the test.
